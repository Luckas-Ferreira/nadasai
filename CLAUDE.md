# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

The product is **Nada Sai** (`nadasai.com`; the repo, the npm package and the `dist/` folder are all `nadasai` — the local working directory is still named `imgwork`, which is the last trace of the old name and matters to nothing) — a client-side file toolbox built with Angular 19 + Tailwind 4. **There is no backend.** Every operation runs in the browser via WASM/Canvas, and no file ever leaves the user's machine — that claim is the product, not a footer detail, so keep any new feature client-side. `NetworkProbeService` instruments it at runtime (see *Offline, PWA and the proof*).

Thirty-five tools in five modules, all declared in `core/tools/tools.ts` (`category: 'image' | 'pdf' | 'audio' | 'video' | 'privacy'`):

- **image** — remove-bg, upscale, vectorize, extract-text (OCR), crop, compress, convert, resize, img-to-pdf
- **pdf** — edit-pdf (the editor, with OCR), merge, compress, split, pdf-to-img, pdf-to-word, organize, protect, sign, watermark
- **audio** — cut-audio, merge-audio, convert-audio, compress-audio, normalize-audio
- **video** — screen-recorder, video-to-audio
- **privacy** — encrypt-file, encrypt-text, file-hash, password-generator, remove-exif, redact-image, redact-pdf, clean-pdf-metadata, diff-checker

**`pdf-to-word` writes .docx and reuses the editor's extraction wholesale.** `docx` (MIT, dynamically imported like jspdf and pdf-lib) is only the writer; the reading is `PdfLoaderService` + `mergeNativeParagraphs` for a digital page and `OcrService.recognise` for a scanned one, both already tuned against real documents. Two things had to be added on top, and both are about a .docx being *linear and handed off* where the editor's output is *absolutely positioned and on screen*. The mergers return blocks in group-creation order, which no previous consumer cared about — unsorted, a scan came out with every line's right half before its left half, all words present and unreadable, which reads as an OCR fault rather than an ordering one (`inReadingOrder`, bands by vertical overlap; a tolerance comparator was tried first and is not transitive, so `Array.sort` could return any permutation). And the OCR font estimate needs its own clamp: a rasterised transcript produced 1pt–42.5pt against 5–12pt on the *native* read of the same file, and 1pt in Word is invisible with nothing on screen to blame. `clampOcrFontSizePt` bounds it relative to the page median and then absolutely — in that order, or a junk page's high median lifts the relative floor above the absolute ceiling and pins the whole page.

Three libraries divide the PDF work and the split matters: **pdf.js** reads and rasterises (always through `core/pdf/pdfjs.ts`), **pdf-lib** writes page-level output (the `features/*/services/*.service.ts` layer), and **jspdf** builds a PDF out of rasters — images→PDF in `core/image/converters.ts`, and `protect-pdf`, which needs encryption pdf-lib cannot do. Note that protect-pdf imports jspdf **statically**, unlike everywhere else; it is inside a lazy route so the initial bundle is safe, but it is a deviation, not the pattern.

## Commands

```bash
npm start                 # ng serve → http://localhost:4200
npm run build             # production build → dist/nadasai
npm test                  # Karma + Jasmine in Chrome (watch mode)
npm test -- --watch=false --browsers=ChromeHeadless   # single CI-style run
ng test --include='**/converters.spec.ts'             # run one spec file

npm run e2e               # Playwright, HEADED — drives the tools in a real window
npm run e2e -- 04-convert # one spec file
npm run e2e:ui            # interactive runner
npm run e2e:report        # last HTML report

npx playwright test -c playwright.debug.config.ts debug-table   # a diagnostic probe (see below)
```

**There is no linter and no formatter.** No ESLint, Prettier or `npm run lint` — `tsc` under `strict` + `strictTemplates` is the only gate besides the tests. Do not invent a lint step; match the surrounding file instead.

`e2e/debug-*.spec.ts` are **not** part of the suite — `playwright.config.ts` ignores them by `testIgnore` and they only run through `playwright.debug.config.ts`. They read a real PDF dropped at the repo root, which `/*.pdf` in `.gitignore` keeps out of git precisely because those documents are somebody's real records (CPF, RG, address). A probe that finds no file skips.

`cypress/`, `cypress.config.js` e os scripts avulsos `test-*.js` / `test-tesseract*.mjs` **foram removidos** — eram dead weight (não havia cypress no `package.json`; a suíte precedia o Playwright) e estão no histórico do git se alguém precisar. Playwright é o runner de e2e, e é o único.

**Há CI, em `.github/workflows/ci.yml`.** Três jobs: `tsc` nos três projetos + testes unitários; build com prerender (que é a única checagem que enxerga código dependente de `window` rodando no Node) e a conferência de que `sitemap.xml` e `llms.txt` commitados batem com os gerados; e a suíte Playwright. `public/model` e `public/tessdata` são cacheados pela chave dos scripts de download, senão cada execução baixa 46 MB à toa. **`tsconfig.e2e.json` existe por causa disso**: o Playwright transpila os specs sem checar tipo, então até o CI um erro de tipo em `e2e/` só aparecia como falha de execução, com dois servidores no ar.

**The background-removal model is fetched at install/build time, not committed.** `scripts/fetch-model.mjs` runs on `postinstall` and `prebuild`; it downloads the 42 MB int8 IS-Net once into `public/model/`, sliced into ~22 MiB parts + a manifest, and is a no-op once the parts are on disk. So `npm ci && npm run build` on a fresh box produces a complete deploy — but if `public/model/` is empty and you skip install, the remove-bg tool 404s on its weights. Do **not** commit these files or swap the source to an RMBG/BRIA checkpoint (non-commercial licence only — see `fetch-model.mjs`).

**Hosting requires COOP/COEP headers.** Remove-bg runs multithreaded WASM, which needs `SharedArrayBuffer`, which needs `Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy: require-corp`. `ng serve` sends them (`angular.json` serve `headers`) and so does the e2e preview server; a static host that omits them silently drops inference to single-threaded (~6× slower), not broken. Anything you embed cross-origin must then be CORP-compatible.

**Every runtime asset is self-hosted, and that is not optional.** `require-corp` blocks cross-origin subresources without CORP, so a library that fetches its own worker/wasm/weights from a CDN does not degrade — it fails outright. It also contradicts the footer's privacy claim, which is why `@imgly/background-removal` was dropped. Three libraries default to a CDN and are pinned to same-origin paths instead, all resolved from `document.baseURI` (never relative — routes are `/pt/…` and `/en/…`, so a relative path lands in the SPA fallback and comes back as `index.html`, which the browser then rejects on MIME):

| asset | served from | copied by |
|---|---|---|
| `ort/` — onnxruntime wasm | `node_modules` | `angular.json` assets |
| `pdfjs/pdf.worker.min.mjs` | `node_modules` | `angular.json` assets |
| `pdfjs/{wasm,iccs,standard_fonts,cmaps}/` | `node_modules` | `angular.json` assets |
| `tesseract/` — OCR worker + core wasm | `node_modules` | `angular.json` assets |
| `model/` — IS-Net weights (42 MB) | download | `scripts/fetch-model.mjs` |
| `tessdata/` — por+eng traineddata (~4 MB) | download | `scripts/fetch-tessdata.mjs` |

Both fetch scripts run on `postinstall` and `prebuild` and no-op once the files exist. Neither directory is committed. The OCR core variants are the `-lstm` ones specifically, because `OcrService` builds its worker with OEM 1 (`LSTM_ONLY`); changing the OEM means copying the Legacy variants too, or the core 404s.

**OCR renders the page at 3×, and the scale is not cosmetic.** `OCR_RENDER_SCALE` in `pdf.component.ts` feeds Tesseract ~216 DPI. It used to be `1` — justified by a comment claiming the bboxes had to map 1:1 onto the displayed page, which is false: `OcrService` normalises every bbox by `canvas.width/height`, so any scale maps identically. What `1` actually did was hand Tesseract an A4 at 72 DPI, well under the ~150 it needs, and a starved Tesseract returns bad *geometry*, not just bad characters. On a photographed form the dense page came back with a median word bbox of 27px where the glyphs were ~8px — 3× inflated — and since `getBaseFontSize()` derives the font body from bbox height, those blocks rendered 3× too large. The sparse page of the same file, easier to segment, measured correctly. Raising the scale fixed the sizing *and* the reading (`24/08/1830` → `24/08/1930`). If OCR sizing ever looks wrong again, check the input resolution before touching the font maths.

`OcrService` still clamps two things as defence in depth, and both earn their place — the max block is exactly at the cap on real documents. `clampOutlierHeights` bounds box geometry; `assignFontSizes` bounds the rendered font at 1.8× the page median. The clamp is on the **font size**, not the bbox: capping only `h` leaves the multiplier spread (1.92/1.06 = 1.8×) to still produce 3.25× on screen. A rejected alternative is recorded in that function — taking the *line* median instead of the per-word estimate is intuitive and measurably worse, because on a noisy scan the line median inherits the bad tokens and propagates them to the good words.

**The PDF editor rasterises by viewport, and that is what keeps sharpness independent of document length.** Only pages near the viewport hold a canvas backing store; the rest are released (`releaseCanvas`) and re-rasterised when scrolled back to. This is not just a memory optimisation. While every page was rasterised at once, the only defence against exhausting canvas memory was to derive the scale from a pixel budget divided by `pageCount` — so a 20-page edital rendered at ~1.5× and looked like a fax, while the HTML text of a selected block stayed vector-sharp beside it. With a fixed window, `pageRenderScale` receives `RENDER_WINDOW` instead of `pageCount` and a 200-page document is as sharp as a two-page one. Two consequences worth knowing: the raster scale tracks the *display* zoom (a fixed scale means zooming past the supersample factor just stretches pixels), and a released page is not blank — `canvasRendered` loses its entry, so the text overlay switches back to painting black text and the page stays readable and editable until it is rasterised again. Rasterisation is serialised behind a mutex because two renders on one canvas race: the second sets `canvas.width`, which clears, while the first is still painting.

**O app é ZONELESS.** `app.config.ts` usa `provideExperimentalZonelessChangeDetection()` e `angular.json` não lista mais `zone.js` nos polyfills do build (os de TESTE continuam com ele: o TestBed sem zone exige provider próprio em cada spec, e isso é uma mudança independente). O pré-requisito já estava pago antes da migração — `NgZone` não aparece em lugar nenhum, `fakeAsync`/`tick` não aparecem em nenhum dos 570 specs, e todo componente é OnPush com estado em signal. Medido: o chunk de polyfills sumiu do HTML servido, e o JS de entrada da home caiu de **34,7 kB gz para 22,1 kB gz**. O que quebra em zoneless, se voltar: estado em campo comum (não signal) escrito dentro de `setTimeout`, `requestAnimationFrame` ou callback de terceiro — a tela simplesmente não atualiza, sem erro nenhum.

**pdf.js needs `Promise.try` to forward its extra arguments.** Era o zone.js que o removia — ele trocava o `Promise` global por um `ZoneAwarePromise` sem `Promise.try` — e sem zone.js o polyfill de `core/pdf/promise-try.ts` virou rede de segurança para navegador antigo (`Promise.try` é de 2024: Chrome 128, Safari 18.2, Firefox 134), com o guarda de `typeof` tornando-o no-op onde já existe. What matters is not that it exists but that it forwards `...args`: pdf.js's `MessageHandler` dispatches every worker action as `Promise.try(action, data.data, streamSink)`, and an arity-1 polyfill satisfies `typeof` while calling each action with nothing. The failure then surfaces three hops away — the action destructures `undefined`, pdf.js wraps it as `UnknownErrorException`, and the console shows `getOperatorList - ignoring XObject` once per image. Because each image is registered as a *dependency* of the operator list and that dependency never resolves, **`page.render()` stays pending forever**: the canvas is left half-painted (pdf.js paints in chunks), no error is ever thrown, and the editor's overlay stays in its "canvas failed" branch, drawing black text on top of the canvas text. There were once two copies of this polyfill, in `main.ts` and in `pdfjs.ts`, both arity-1; fixing the second changed nothing, because the first runs at bootstrap and the other's `typeof` guard then found the broken one already installed. One implementation, imported by both. `promise-try.spec.ts` asserts the forwarding, not the existence.

**`tesseract.js` is CommonJS and must be imported through its default export.** Vite (dev) synthesises named exports from CJS; esbuild (prod) emits `export default` alone. So `const { createWorker } = await import('tesseract.js')` works under `ng serve` and yields `undefined` in a production build — surfacing as a minified `"e is not a function"` nowhere near the cause. `loadCreateWorker()` in `ocr.service.ts` reads the default with a fallback. Any other CJS dependency imported lazily has the same trap.

E2E lives in `e2e/`. It uploads a real image, runs each tool and asserts on the actual `download` event (the suggested filename is what proves both the encode and the naming rules). `e2e/fixtures/generate.ts` synthesises the fixtures at startup — a hand-rolled PNG encoder, so no binaries in the repo. **The grain in that PNG is load-bearing**: a flat synthetic image compresses smaller as lossless PNG than as lossy WebP, so `compress` legitimately produces a bigger file and the savings badge never renders. Playwright runs **two** web servers: `ng serve` on 4200 for most specs, and a real production build behind a static preview server on 4300 for `09-offline`, `21-prerender` e `36-csp` — `ng serve` never emits `ngsw-worker.js`, so the offline/service-worker assertions need the actual build artifact. **As duas portas saem de `e2e/ports.ts`** e aceitam `NADASAI_DEV_PORT` / `NADASAI_PREVIEW_PORT`: 4200 ocupada na máquina de quem desenvolve derrubava a suíte inteira por um motivo sem relação com o produto. E a suíte roda **headless quando `CI` está definido** — `headless: false` num runner é "Missing X server", não lentidão.

A cobertura funcional cobre hoje 33 das 36 ferramentas (`27`–`35` fecharam as 14 que faltavam, incluindo o editor). Duas coisas achadas ao escrevê-las valem registro: `split-pdf` escreve `doc_split_files.zip` / `doc_range_1.pdf` e `pdf-to-word` escreve `doc.docx`, ou seja, **as duas ignoram o `suffix` que declaram em `tools.ts`** — os specs pinam o comportamento atual, porque renomear download é decisão de produto e não efeito colateral de teste. E o teste que mais importa no editor é o do canvas PINTADO (`33-edit-pdf`): ele lê pixels de volta, porque a falha do `Promise.try` deixa a página meio pintada sem lançar erro nenhum.

**Specs 16–20 cover the privacy module, and they assert the guarantee rather than the screen**: the file comes back byte-identical from an encrypt→decrypt roundtrip, the digests match what Node computes, the stripped PNG has lost the author's name *and* still contains the original IDAT (the second half is what separates a strip from a re-encode), and the cleaned PDF has no trace of the author in the **decompressed** object streams. Two of them needed fixtures with something to find — `PHOTO_META` (tEXt/tIME chunks) and `DOC_META` (`/Info` + XMP) — because "no metadata found" is the one result that passes whether the parser works or not. Writing them found two dead features: `app-region-overlay` measured its own host, which is an inline element with a 0×0 box, so every drag normalised to a degenerate rect and **no redaction box could ever be drawn**, in either redact tool. Raw `page.mouse` drags skip Playwright's actionability checks, so `drawRegion` in `e2e/helpers.ts` waits for the splash overlay explicitly — while it is up it swallows every pointerdown, and a locator click would have retried past it.

## Architecture

### The chain (`WorkspaceService`)

`core/services/workspace.service.ts` holds ONE `WorkSession { file, kind, originalName, history, past, pdfPassword }` for the whole product, and it is the only shared state. It replaced `ImageStateService` + `AudioStateService`, which were the same service twice with a different `assertUsable*` in the middle — and, more to the point, two sessions that could not see each other, which is why a PDF built out of photos or an audio track pulled out of a video hit a download button and stopped.

Three pieces make a tool part of it, and none of them is optional:

1. `hydrateFromWorkspace(toolId, onFile)` in the constructor. It is an **effect**, not a constructor read, and that is what makes undo work without navigating: the old bar did `navigate(['/'])` purely to force the open tool to be rebuilt around the restored file, which threw the user out of the tool *and* switched their language, because the `''` route is a `redirectTo: 'pt'`.
2. `workspace.load(file, toolId)` on upload — and nothing else. Decoding, previews and clearing the last result belong in the hydration callback, so the "dropped here", "arrived through the chain" and "came back through undo" paths are one path. They used to be two, and the third did not exist.
3. `pendingTransition.registerResult(toolId, blob, suffix, ext)` when a result is ready. Committing is the navigation's job (below), so the tool never applies anything itself.

**`accepts` / `produces` on the `ToolDef` is what the chain is made of.** `accepts` is the list of `FileKind`s the tool can open (`[]` = takes no file, `['any']` = literally anything, which is what makes encrypt-file and file-hash the end of every chain); `produces` is what it hands back, or `null`. `nextToolsFor(kind, fromId)` derives every destination from those two fields, so the chips, the file bar's "Enviar para…" and the hydration guard all agree by construction. It replaced `chainableImageTools`, a hand-written list of six image tools — which is why the chain existed only in the image module, and why even there it left out `vectorize`, `extract-text` and `img-to-pdf`, three tools that accept an image perfectly well.

Four invariants live here, and all four are load-bearing:

- **The type guard is at the PICK-UP, not the drop-off.** `fileFor(toolId)` hands the session over only when the tool's `accepts` covers the session's `kind`. This is strictly stronger than the old "`apply()` rejects anything that isn't `image/*`": crop still cannot receive a PDF, and img-to-pdf can now feed the PDF module, which the old guard made impossible. A tool that reads `currentFile()` directly bypasses it and reintroduces the bug.
- **Filenames derive from `originalName`, never from the current file.** `photo.jpg` → `photo-nobg.png` → `photo-crop.png`, not `crop-nobg-photo.jpg`. This is also why a commit is `apply()` and never `load()`: `load()` starts a NEW session, so `history` and `past` are wiped and the name starts deriving from the result. Upscale's commit did exactly that, and silently erased the breadcrumb and the undo stack of everything before it.
- **`undo()` re-derives the kind rather than remembering it.** Undoing past img-to-pdf takes the session from a PDF back to an image, and a stale `kind` would then offer that image to the PDF tools.
- **A tool that commits its own result gets hydrated with it, and must survive that.** Only two do — `cut-audio` and `video-to-audio` call `workspace.apply()` inside `run()` instead of registering a pending commit — and for both it is deliberate: the cut BECOMES the working file so you can cut again, and the extracted audio has to reach the audio module. But `apply()` changes the session, the effect fires, and the tool's own `onFile` runs against its own output. The cutter's callback cleared `result`, so the "Baixar" button vanished in the same frame it appeared and the cut audio had no way out of the page at all; the extractor's callback got `null` (the session is audio now, and it `accepts: ['video']`) and wiped the video, the result and the button. Both now ask `history().at(-1)` whether the change was theirs — the session already records who produced the current file, so no new state was needed. Any future tool that commits inside `run()` inherits this and nothing warns you: the screen is simply blank where the result was.

**The commit runs on `NavigationStart`, in `PendingTransitionService`.** It used to be a `(click)` handler on the rail and on the mobile bar, which meant those two carried the result forward and every other way out of a tool dropped it: the command palette, the module switcher, the "Módulos" link, the Back button and a typed URL — four of which are the only ways to LEAVE a module, so crossing modules was exactly the case that lost the file. One subscription replaces all of it, and it is also why the registration is self-cleaning: by the time a component is destroyed, its commit has either run or been cleared.

**`app-file-bar` is the one persistent band**, for all five modules. It replaced `app-current-file-bar` and `app-current-audio-file-bar`, which had drifted (only one had a thumbnail and the pending dot; only the other had the format tint), and left PDF and privacy with no breadcrumb and no undo at all. Its "Enviar para…" exists **before** anything has run, which is the point: the action-bar chips only appear once there is a result, so the chain was invisible to whoever opened the wrong tool first. It is also the only list without `MAX_NEXT_TOOL_CHIPS` — a popover scrolls, a 324px panel does not.

### Writing a tool

Do **not** copy an existing component wholesale — the shared kit in `shared/ui/` exists precisely to stop that. A tool is:

```ts
@Component({ providers: [ObjectUrlScope], ... })   // <- component-scoped, not root
```

with `<app-tool-page [toolId]="'x'">` projecting three slots: `[banner]` (errors), `[stage]` (the image), `[panel]` (controls, wrapped in ONE root element — content projection does not reach through an `@if` with multiple root nodes).

Shared pieces: `app-dropzone`, `app-preview-surface`, `app-compare-slider`, `app-segmented`, `app-panel`, `app-action-bar`, `app-alert`, `[appButton]`, `app-icon`.

`app-action-bar` needs a `[toolId]`, and derives the rest: the chips come from `nextToolsFor(produces, toolId)`, and it navigates on a chip itself, since the commit happens on `NavigationStart` anyway. `[resultKind]` overrides `produces` for the two tools whose output is not fixed: split-pdf and pdf-to-img hand back a zip when they make several files, and offering "sign PDF" for a zip is worse than offering nothing.

`app-action-bar` also takes a **nullable `primaryLabel`**, and every tool passes null once pressing the button could only reproduce the result already on screen. Each computes this as a `stale` signal: the settings its `run()` actually reads, versus the ones the current result was made with (`ranQuality`, `ranSettings`, `ranBox`, …). A primary button that recomputes identical bytes reads as "it didn't work" — on remove-bg it re-ran seconds of inference to land back where you started. Note the mirror-image bug this replaced: the templates once hid the button behind `*ngIf="!result()"`, so changing a quality or format meant re-uploading. The label must come back the instant a setting changes. Remove-bg is the tool to think about here — `run()` reads *nothing* but the file, and the backdrop is composited at export, so its button is simply gone once a cutout exists.

Templates live in a sibling `*.component.html` for every feature. `features/pdf/pdf.component.ts` is the one inline template, and only because it is ~2k lines of editor that nobody should scroll past to reach the class.

**Registering a tool touches five places, and skipping any of them is a silent bug, not a compile error:**

1. `core/tools/tools.ts` — the `ToolId` union and a `ToolDef`, **including `accepts` and `produces`** (`tools.spec.ts` enforces both; forgetting them does not break the tool, it silently drops it out of the chain, which is worse). The rail, the home grid, the mobile bar, the palette and the filename suffix all read from here, and the tool's `category` must be an id in `MODULES` (`tools.spec.ts` enforces it — `moduleById` throws, so a stray category takes the shell down on that route rather than degrading). `tone` must also exist as `tone-<value>` in `styles.css`, in both halves (the utility and the token pair).
2. `app.routes.ts` — **two** entries, `pt/<caminho-em-português>` and `en/<english-path>`, each with `title` + `data.metaDescription`/`metaKeywords`, plus a legacy redirect if the path ever shipped under another URL. The file is a long literal list on purpose: these are indexed URLs.
3. ~~`core/services/seo.service.ts`~~ — **nothing to do.** `core/seo/route-map.ts` now DERIVES the hreflang map from `TOOLS`, registering one shared object under both spellings. The hand-written map this replaced was missing 7 of 28 tools — a 25% failure rate on this very checklist — and the fallback then advertised alternates pointing at URLs that do not exist, which makes Google discard the annotation for the whole cluster. `route-map.spec.ts`, the path-uniqueness test in `tools.spec.ts` and `app.routes.spec.ts` now make the omission impossible rather than merely discouraged. If you add a tool, the only new obligation is `core/seo/tool-content.ts` (below) — and a tool with no entry there falls back to the generic FAQ rather than breaking.
4. The EN and PT dictionaries in `translation.service.ts` — `navKey`, `shortKey`, `titleKey`, `descKey`. This one *is* a compile error (see i18n), which is the point.
5. `ngsw-config.json`, but only if the tool pulls a new runtime asset directory; the existing groups already cover `pdfjs/`, `tesseract/`, `tessdata/`, `model/`, `ort/`.
6. `npm run og` — os cards sociais e os ícones do PWA são gerados por Chromium e COMMITADOS, fora do `prebuild` de propósito (o deploy do Pages não pode baixar um navegador). Sem rodar, a ferramenta nova herda o card padrão; `og-cards.spec.ts` falha e diz o comando, em vez de deixar passar.
7. `core/seo/tool-article.ts` — o texto longo, nas duas línguas. `tool-article.spec.ts` cobra: entrada para toda ferramenta, mesmas seções em PT e EN, 400 palavras no mínimo por língua e as duas dentro de 25% uma da outra. O critério do conteúdo é o mesmo do FAQ: cada parágrafo precisa dizer algo que só vale para AQUELA ferramenta — o limite real, o formato que ela escreve, a troca que ela faz.

The language is derived from the URL prefix, not stored: `TranslationService` subscribes to `NavigationEnd` and flips on `/en` vs `/pt`. So a tool reachable only under one prefix is a tool half the site cannot see.

Adding a **module** is `MODULES` in `tools.ts` plus `module.<id>` / `module.<id>_desc` in both dictionaries. Nothing in the shell or the home page needs touching: the rail, the switcher, the mobile bar, the palette and the home grid all walk `MODULES`.

### The shell (`app.component.html`)

Three surfaces, and which of them exist depends on where you are:

- **`app-top-bar`** — always. Wordmark, the module switcher, the palette trigger, and the live network meter. It is the only place the brand is stated (the rail used to carry a 24px copy of it, and the mobile header a second one), and — because it is the one surface on every route, and sticky — it is also the only place the meter can live if the meter is to be present while a file is actually open. It is `sticky` **on the host**, not on the `<header>` inside it: the host is a flex item, so it is blockified to exactly the header's height, and a sticky child of a box its own size has no room to travel and simply scrolls away.
- **`app-tool-nav`** (the rail, desktop) and **`app-mobile-tool-bar`** — only inside a module. Both list the tools of the *current* module and nothing else.
- **`app-command-palette`** — always, `⌘K`/`Ctrl K`, reaching every tool of every module.

**The rail is scoped to one module, and that is the whole design.** A global rail has a hard ceiling: at 15 tools the list already ran past the bottom of a 700px window, and the container had no `overflow-y-auto`, so the last PDF tools were simply unreachable. Adding a scrollbar treats the symptom — the length of a global list grows with the product. Scoped, the rail's height tracks the size of a *module*, so the tenth module costs nothing in that layout. Two consequences carry the rest of the design:

- Crossing modules needs a control that is always present, hence the switcher in the top bar; and finding a tool by name needs something that ignores scoping, hence the palette. **Neither is decoration — remove either one and part of the product becomes unreachable from a tool page.** The switcher lands on a module's *first* tool because there is no per-module landing route (adding one means two localized paths plus an SEO mapping); the rail reveals the rest on arrival.
- No module → no rail and no mobile bar (home, `/sobre`, `/faq`). Those pages are the launcher and the reading; the home grid *is* the navigation there, and `main` gets the full width.

`ActiveToolService` resolves "where am I" by matching the URL against the declared `pathPt`/`pathEn` — never by path prefix, because `img-to-pdf` lives at `imagem/para-pdf` while the PDF module lives under `pdf/…`, so a prefix rule files it in the wrong module. It reads `urlAfterRedirects`, which is what makes it survive the legacy redirects.

The mobile bar is **one** scrolling row with the active tool pulled into view on navigation. It was a `grid-cols-5`, honest to its comment ("everything at once, nothing behind a scroll") only while a module had five tools; with nine it silently became two rows. The auto-scroll is what makes the row acceptable — the scroll strip *it* replaced was abandoned because the current tool could sit off-screen with nothing saying so.

**`img-to-pdf` keeps its SOURCE list off the chain, and that is not an oversight — merge-pdf and merge-audio follow the same pattern.** The session holds exactly one file — that is what makes the other tools chainable — and a reorderable page list is not a chain, so the list is local component state, read from the session ONCE in the constructor rather than through `hydrateFromWorkspace`: reacting to the session would throw away the order the user just arranged every time the file changed. Its RESULT, on the other hand, does go into the session, and that is what finally connects the image module to the PDF one — until `WorkspaceService`, the tool that produces a PDF was forbidden from handing it over. Consequences worth knowing: `<app-tool-page>` gets `[forceLoaded]` because its default `loaded` watches the chain, which is empty here; the output filename comes off **page one**, not `originalName`; and `stale` has to include the page order, or dragging page 3 to the front would leave the stale PDF downloadable. `app-dropzone` grew `multiple` + `filesSelected` for it — emitted *alongside* `fileSelected`, never instead of it, so the five single-file tools are untouched.

`encodePdfFromImages` in `core/image/converters.ts` backs it, and `encodePdf` is now a one-line wrapper over it. Two things there are load-bearing: the loop is **sequential** (mapping it through `Promise.all` holds every decoded canvas at once — thirty 12 MP photos is gigabytes of RGBA), and `maxLongSide` caps the raster for the multi-image path only. Without the cap a batch of phone photos builds a 50 MB PDF at 2-3 MB per page; single-image convert passes no cap, because there the user asked for that one image at full resolution.

### Object URLs

`ObjectUrlScope` (`core/image/object-url.ts`) must be in every tool's `providers`. Angular destroys it on route leave, which is the entire point — provide it in root and you have recreated the leak it was written to fix. Use `urls.replace(old, blob)` rather than raw `createObjectURL`.

### Image pipeline

All format logic lives in `core/image/` and is unit-tested; components should not touch canvas directly.

- `converters.ts` — `encodeImage`, `resizeImage`, `encodePdf`, `encodeIco`, `compressImage`
- `image-file.util.ts` — `loadImage` (rejects on error), `canvasToBlob` (rejects on null), `drawToCanvas`, `flatten`, `suffixedName`, `formatBytes`, validation
- `download.ts` — `saveBlob` via file-saver

Three constraints worth knowing before you "improve" this:

- **AVIF is not an output format, deliberately.** `canvas.toBlob('image/avif')` is unsupported and, per the HTML spec, *silently falls back to PNG* — it does not throw or return null. The app used to ship PNG bytes in a `.avif` file. AVIF is still accepted as input. Adding real AVIF output needs a WASM encoder.
- **Anything without an alpha channel (JPEG, PDF) must be flattened first**, or transparency serializes as black. `encodeImage`/`encodePdf` already do this; a pixel test guards it.
- **`jspdf` is lazily imported** inside `encodePdf`. It drags in html2canvas (~350 kB); importing it statically put that in the convert chunk for everyone. Keep it dynamic.

### PDF tools

Nine of the fifteen tools are PDF tools and they share almost nothing with the image chain. The shape is always the same, so read one (`split-pdf` is the plainest) before writing another:

- **`core/pdf/pdfjs.ts` is the only door to pdf.js.** `getPdfjs()` memoizes the import and pins the self-hosted worker; `openPdf(file, password?)` validates the type, enforces `MAX_PDF_BYTES` (100 MB) and maps pdf.js failures onto `pdf_encrypted` / `pdf_unsupported`; `closePdf` tears down the worker; `releaseCanvas` drops a backing store. Do not call `getDocument` yourself — every call must carry `pdfAssetUrls()`, and the failure mode when it doesn't is *not* an exception. pdf.js logs and continues, so the page renders with pieces missing (that is how the logos vanished from an academic transcript: the missing decoder was `openjpeg.wasm`).
- **Render into the canvas that is already in the DOM** (`renderPageIntoCanvas`), not into an offscreen one you then blit. Two canvases alive at once is 2× video memory — ~40 MB per A4 at 3.2× — and a browser over the limit does not throw, it hands back a blank canvas.
- **Each tool owns a stateless `providedIn: 'root'` service under `features/<tool>/services/`.** It takes Files and options, returns a Blob, throws `AppError`, and reports progress through a callback. All UI state stays in the component, which is what lets Angular drop it on navigation.
- **`pdf-lib` is imported dynamically in every one of those services** (`const { PDFDocument } = await import('pdf-lib')`), same reasoning as jspdf: nobody who came to crop an image should pay for it. Type-only imports are fine and are used (`import type { PDFFont }`).
- **Password-protected files are a two-step flow, not an error.** `openPdf` throws `pdf_encrypted`; the component parks the file in a `pendingFile` signal, shows `<app-pdf-password-prompt>`, and re-opens with the password, which is then threaded through every later `openPdf` call for that document.
- **The lib choice per tool is forced by capability, not preference.** pdf-lib rearranges pages and draws on them (merge, split, organize, sign, watermark, the editor's export) and it can neither rasterise nor encrypt — so compress-pdf's lossy levels and protect-pdf go through pdf.js + a re-encode instead, which is why both destroy vector text. compress-pdf compensates by re-drawing the old text layer invisibly over the raster so Ctrl+F still works; `PdfExporterService` uses the same trick to make OCR'd scans searchable.
- **A marca d'água desenha pela MESMA conta que a prévia, e é isso que a torna uma ferramenta.** `core/pdf/watermark-layout.ts` é puro e devolve os pontos de desenho; o serviço os manda para o pdf-lib e o componente os pinta num canvas por cima da página 1 rasterizada. Enquanto a prévia era um `<span>` com `rotate()` e `fontSize * 0.75` sobre uma `<img>`, ela não sabia de repetição, de posição nem de logo — mostrava "CONFIDENCIAL" no meio e escondia o resultado real até o download. Três coisas moram na função pura porque as duas pontas divergiriam sozinhas: a origem de desenho (o pdf-lib gira em torno do canto, não do centro, então centralizar a caixa NÃO girada jogava o texto a mais de 100pt do lugar a 45°), a grade que gira junto com a marca (uma grade reta com itens tortos não é a mesma coisa, e cobrir só a largura deixa os cantos vazios em qualquer ângulo que não seja múltiplo de 90°) e a entrelinha do bloco de várias linhas. O teto de `MAX_MARKS_PER_PAGE` existe porque cada marca é um comando no content stream: um texto de 8pt lado a lado passa de mil por página, engorda o arquivo e entrega um borrão — quando ele aperta o passo, o painel diz que apertou, como o crossfade de juntar-áudio. O logo é embutido UMA vez e desenhado muitas; embutir por marca copiaria os bytes da imagem a cada uso.
- **`merge` copies per source *file*, not per page.** `copyPages` clones the resource tree it walks, so calling it once per page duplicates shared fonts and colour profiles until the merged file is larger than its inputs. The copies are then consumed in insertion order, never looked up by page index — keying by index collapses a page used twice into one object and produces a corrupt file.
- `app-page-grid` is the reorderable thumbnail strip, shared by img-to-pdf and merge-pdf; it knows nothing about Files, only a label and a URL. Drag-and-drop is the shortcut, the arrow buttons are the real control (drag does nothing on touch or from a keyboard).
- **`fflate` (zip output for split-pdf and pdf-to-img) is a declared dependency**, as of the privacy release. It used to resolve only because jspdf depends on it — a transitive dependency that would have vanished with a jspdf upgrade.

### Audio (`core/audio/`, `features/cut-audio/`, `features/merge-audio/`)

Six tools. The Web Audio API decodes, and everything else is arithmetic over Float32 in `core/audio/` — the only dependency the module has is the MP3 encoder (below). Same split as the image pipeline: pure and unit-tested in `core/`, UI state in the component, one stateless service per tool doing the work.

- **WAV is what `core/audio/` writes, and MP3 arrived later through one file.** The browser decodes MP3/OGG/M4A/AAC/FLAC and can write none of them, and every JS MP3 encoder worth using is a LAME port — which is why `encodeWav` exists and why the cut is never re-encoded. `@breezystack/lamejs` is now a dependency and `AudioConverterService.encodeToMp3` is the single door to it (convert-audio owns it; compress-audio and normalize-audio inject that service rather than importing the encoder). WAV stays the default wherever the tool's job is not to shrink the file, because a re-encode is a second generation of loss on top of whatever the source already lost. The header comment in `wav.ts` still argues the pre-lamejs position; the dependency list is the truth.
- **`MAX_AUDIO_SECONDS` (30 min) is a memory ceiling, not a policy.** `decodeAudioData` expands to 32-bit float PCM — 30 minutes of stereo at 48 kHz is ~690 MB resident, and the cut allocates the result on top of it. The 100 MB byte limit alone does not guard this: a 100 MB MP3 is ~100 minutes and would ask the tab for over 2 GB. The duration is only knowable after the decode, which is where it is checked.
- **`decodeAudioData` resamples to the context's rate**, i.e. the output device's. A 44.1 kHz file on a 48 kHz device is exported at 48 kHz. There is no API to decode at the file's native rate; this is a floor, not a bug.
- **`AudioEngine` is a plain class the component owns, not a `providedIn: 'root'` service** — the one deviation from the PDF-tool shape, and for the reason recorded under background removal: a live AudioContext and running source nodes are per-run state, and in a singleton they outlive the navigation that should have ended them. A root-scoped player keeps a track playing over the tool you moved on to.
- **Peaks are computed once per file at a fixed 131072 buckets, never from the canvas width and never per scroll position.** A pass costs O(samples), not O(buckets), so the large count is free and covers every zoom level; the draw slices the bucket range the window covers and downsamples from there. Deriving the count from the width re-scans the whole buffer on every ResizeObserver callback (a quarter-second freeze each, continuously, while a window is dragged), and recomputing per view re-scans a third of a podcast on every scrollbar tick. The peaks are min/max per bucket, not a strided sample: a stride reports whichever single sample it lands on, so quiet passages sprout spikes and the shape flickers as the window moves.
- **The waveform reads on the same surface as a PDF page**, and deliberately so: `doc-stage` surround, white sheet, `rounded-md`, `shadow-page`. It is a document you scrub, not a picture whose brightness you are judging, so `bg-stage` does not apply — same argument as the editor's scrolling surface.
- **Zoom scrolls the SURROUND and pins the sheet.** The spacer inside the scroller is as wide as the whole timeline at the current zoom; the sheet is `sticky left-0` at exactly `viewWidth()`, and the canvas only ever paints the window in front of it. A canvas as wide as the timeline would pass the browser's maximum canvas size at any real zoom on a long track — and the native scrollbar, momentum and trackpad gestures come for free. The sheet's width must be **bound**, never `w-full`: `w-full` resolves against the spacer, so at 40× the sheet became 30000px, the canvas stretched its 750px backing store across all of it, `sticky` had nothing to pin, and every pointer x mapped to the wrong second.
- **Anything that changes the spacer's width must set `scrollLeft` on the next frame, not immediately.** The width is a binding, so it is only that wide after the render; scrolling before then lands against the old width and snaps back.
- **`AudioEngine` plays a list of CLIPS, one gain node each, and that is what makes a crossfade expressible at all** — an overlap needs one clip ramping down while another ramps up, which a single shared envelope cannot say. With no crossfade the clip gains sit at 1 and the master carries the fades and splice dips exactly as before, which is why the cutter's behaviour did not change when merge-audio arrived.
- **Crossfades are equal-power (sin/cos); plain fade in/out is linear.** They are different jobs and the difference is audible: two LINEAR ramps crossing sum to 0.5 in amplitude at the midpoint, about -6 dB, which is a hole in the middle of every transition — sin/cos keeps the sum of squares at 1. A single fade has nothing to sum with, and there linear is what the number in the panel promises (two seconds of fade means half level at one second). `audio-merger.service.spec.ts` pins the crossfade one by merging a constant tone with itself and asserting the level does not sag.
- **A crossfade is clamped to half the shortest track, in the service AND in the readout.** Longer would make that track's own fade-in and fade-out collide — and on the playback side two overlapping `setValueCurveAtTime` calls on one param throw. The panel says when it clamped rather than quietly applying a different number than the field shows.
- **merge-audio widens mono up to the widest track, never folds stereo down.** Dropping a mono voice note next to a stereo song is the whole point of a joiner; taking the narrowest instead would silently mono a mix because one clip was a voice memo.
- **`app-page-grid` is reused for the track strip.** It knows only a label and an image URL, so giving each track a rendered picture of its own waveform (`renderPeaksToCanvas`) buys the same drag-to-reorder, the same arrow buttons and the same page-sheet styling the PDF tools have — a bespoke track list would have been a second implementation of all of it.
- **The splice dip is applied after all segments are copied, never during.** `remove` joins two pieces that were never adjacent, which is a click; ramping ~4 ms down into the join and back up hides it. Dipping inside the copy loop ramps samples the next `set()` has not written yet, so the fade-in half is overwritten and the click comes back on the second side only. `audio-cutter.service.spec.ts` pins exactly that.
- **`normalize-audio` measures before it offers anything, and the measurement is BS.1770, not an RMS.** `core/audio/loudness.ts` is the K-weighting plus the two-stage gating, and the filters are *derived* for the file's sample rate (the libebur128 formulation) rather than copied from the spec's 48 kHz table — the table applied to a 44,1 kHz file shifts both corners ~9%, which is a small systematic error sitting directly under the number the panel prints. `loudness.spec.ts` anchors the scale on EBU Tech 3341 case 1 (stereo 1 kHz sine at -23 dBFS reads -23,0 LUFS); every other test there is a relation — doubling, channel summing, the gate — and relations survive a wrong offset, which is why that one test carries the whole calibration.
- **The gating is the feature, not a refinement.** Half a minute of silence after the track drops an ungated mean by ~10 dB, and the tool would answer with an absurd gain. The absolute gate (-70 LUFS) and the relative one (-10 LU below the gated mean) are what make a podcast's pauses stop counting as part of the podcast.
- **The limiter guarantees the ceiling by construction, and that is why it is two passes over an envelope instead of an envelope follower.** A follower reacts *after* seeing the peak, and the peak has already gone out; `Math.min(x, ceiling)` is distortion, which is the one sound a "make it louder" tool cannot produce. `applyGain` builds the per-sample gain that fits under the ceiling, then limits how fast it may RISE — backwards for the attack (read forwards, that is the ramp descending ahead of the peak) and forwards for the release. Both passes only lower values, so the result is bounded by the envelope it started from. The envelope is shared by every channel: per-channel gain moves the stereo image every time the limiter engages.
- **Peak here is sample peak, and the -1 dBFS default ceiling is what pays for that.** True peak needs 4× oversampling before measuring; the decibel of headroom covers the intersample peaks instead, and the panel says so rather than letting the number imply a precision it does not have.
- **In peak mode the ceiling IS the target.** Leaving the two independent let the limiter undo the gain that had just been computed — asking for -0,1 dBFS with the ceiling at -1 produced a file at -1 while the panel promised -0,1. `options()` collapses them and the ceiling selector only renders in loudness mode.
- **The resulting loudness is re-measured only when the limiter engaged.** Limiting removes energy, so reporting the requested target after it would report a number the file does not have; when nothing was held back the answer is exactly `medida + ganho` and costs nothing.
- **The waveform has its own colour tokens (`--color-wave-*`)**, for the same reason the rail does: `--accent` is blue-700, tuned for AAA on white, and against the near-black stage it is a smear. A canvas takes no Tailwind class, so the component reads the tokens off the root element at paint time — still the rule (no hex in a component), resolved at runtime.

### Video (`core/video/`, `features/screen-recorder/`, `features/video-to-audio/`)

Two tools, and the module exists because of a rule the codebase already followed without naming it: **a tool's module is the kind of file it takes IN, not the kind it hands back.** That is why `img-to-pdf` is filed under image while living at `imagem/para-pdf`. `video-to-audio` was in the audio module because of its output; by the same rule it belongs here, and moving it cost nothing — `ActiveToolService` matches declared paths and never prefixes, so its URL (`audio/extrair-de-video`) stays exactly where Google found it, with no redirect, no sitemap churn and no hreflang change.

**`screen-recorder` is the only tool in the product that takes no file at all** (`accepts: []`) — it CREATES one. `getDisplayMedia` + `MediaRecorder`, no dependency, and the source picker is the browser's own, so nothing here can capture anything the user did not explicitly choose. Paired with the network meter it is probably the most direct demonstration of the product's premise there is: a full screen recording that produces zero bytes of egress.

- **`ScreenRecorder` is a plain class owned by the component, never `providedIn: 'root'`.** Same argument as `AudioEngine`, with a far worse failure: a live capture `MediaStream` in a singleton keeps recording the screen after the user has left the tool. In a product called "Nada Sai" that is the worst possible bug, and the only structural defence is for the object to die with the view.
- **The container is the user's choice; the codec is not, and neither is ever read at module scope.** The panel asks WEBM or MP4 and offers only what `MediaRecorder.isTypeSupported` accepts here, because there is no re-encode: the format is the `mimeType` the recorder is *constructed* with, so announcing MP4 on a Firefox that only writes WebM would promise a file that never appears. `availableRecorderFormats()` dedupes the candidate list by container on purpose — the three WebM entries exist to fall from VP9 to VP8 to generic, which is a codec fallback and nobody's decision, and offering three WEBM buttons would expose it as if it were one. With a single format supported the panel prints its name instead of rendering a one-option selector. `MediaRecorder` does not exist in the prerender's Node, so the list is read in the constructor behind `isPlatformBrowser` and the server renders the single-format branch — the `TESSERACT_PATHS` trap, which a module-scope call here would repeat. `25-screen-recorder.spec.ts` drives a real capture (headless Chromium answers the browser's own source picker via `--auto-select-desktop-capture-source`, set in that file's `test.use` rather than in the shared config) and asserts the downloaded extension, which is the only proof that the choice reached the recorder.
- **Two audio sources need an AudioContext; one does not.** A `MediaStream` accepts several audio tracks but `MediaRecorder` records only the first, so handing it both the system track and the mic produces a video with the system sound and no voice — which you find out after recording. With a single source no context is created at all: resampling for nothing is free quality loss.
- **`ended` on the display track is the main way a recording finishes, not an edge case.** "Stop sharing" in the browser's own bar is the button in front of the user the entire time.
- **The 60-minute cap is file size, not memory.** `MediaRecorder` chunks become `Blob`s, which the browser backs with disk — an hour of screen does not live in the heap. At 2.5 Mbps it is ~1.1 GB to download, which is why the limit is announced in the panel and shown by the timer instead of arriving as a surprise.
- **The recording enters the session with `load()`, not `apply()`**, because it starts a chain rather than continuing one — the same reasoning `video-to-audio` used when its source was still outside the session. That is also why `app-action-bar`'s `canContinue` is `hasPending() || workspace.kind() === produces`: a tool that commits immediately has nothing "pending", and with only the first test the recorder offered no next step at all.
- **Deliberately absent from v1:** webcam overlay, region crop, and any re-encode. All three are edits on top of a video this module already produces, none of them changes the capture path, and they belong in new tools here rather than in `ScreenRecorder`.

**`video-to-audio`** — the extraction itself, and the whole design is about not shipping a demuxer.

- **`decodeAudioData` is handed the raw video file, and that is the fast path — not a hack.** Chrome, Edge and Safari demux the container and return the audio track alone, at disk speed and with no loss. `core/video/extract-audio.ts` tries it first, and when it works the extraction is over an order of magnitude faster than the file's own duration.
- **The fallback plays the video and captures it, sample by sample, through an AudioWorklet.** Firefox is why: its pipeline refuses `decodeAudioData` on several containers that carry a video track. The cost is real — it takes the length of the video — so the screen says so, shows the remaining time and offers a cancel. `MediaRecorder` was rejected as the fallback because it would encode to Opus: a WAV built from Opus is the same lie as a PNG named `.avif`. A demuxer + WebCodecs would beat both, and is deliberately absent: it buys speed only where the fast path already failed, at the cost of a container parser, a codec-configuration path and a third set of failure modes. `extractAudioTrack` is the only door, so that is where the swap goes.
- **The worklet is loaded from a Blob URL and buffers 16 384 frames before posting.** Posting every 128-frame render quantum is ~675 000 messages over 30 minutes. The remainder is flushed by an explicit message on `ended`, or the last ~0.34 s of every file is lost. The destination is allocated ONCE from the probed duration and written into at an offset: accumulating chunks and concatenating holds two copies of a 690 MB buffer at the same time.
- **The worklet output goes through a gain of zero into the destination.** A node with no path to the destination is never processed, so `process()` would simply never be called. And the element must NOT be `muted`: several implementations zero the `MediaElementAudioSourceNode` output along with it, and the capture records silence.
- **The duration is probed before a byte is read.** `probeVideo` reads `loadedmetadata` off a detached `<video>`, which costs nothing and refuses a three-hour file before half a gigabyte of ArrayBuffer is allocated. `MAX_VIDEO_SECONDS` (30 min) is the memory ceiling — 32-bit float PCM, ~690 MB for stereo at 48 kHz — and `MAX_VIDEO_BYTES` (500 MB) only guards the fast path's ArrayBuffer.
- **`duration: Infinity` is not a corrupt file; it is every browser recording.** A MediaRecorder WebM — screen capture, webcam, a recorded meeting — carries no duration in its header. Seeking to `1e101` forces the element to settle on the real one. Rejecting it would reject exactly the recording people come here to convert.
- **The result joins the chain through `apply()`, and the source is now a real session.** The session holds a video (that is how the screen recorder hands one over), so extracting keeps the breadcrumb — recording → audio — and an undo that goes back to the video. It used to be `load()`, because `AudioStateService` refused to hold a video and there was no session to continue; `load()` wiped the history and re-derived the name from the result. A long WAV still exceeds the module's 100 MB ceiling, so the hand-off is allowed to fail — the download still works and only the chain step disappears.
- **The compatibility path has no unit test, on purpose.** It needs to play real media, and Karma's headless Chrome has no user gesture, so the AudioContext stays suspended and everything hangs waiting for a permission that never arrives. `e2e/22-video-to-audio.spec.ts` covers it in a real window by making `decodeAudioData` refuse the file once — which is precisely the Firefox behaviour the path exists for. That spec also synthesises its own fixture in the page (canvas stream + oscillator through MediaRecorder), so a genuine video with a genuine audio track exists with no binary committed and no dependency added.

### Privacy (`core/{crypto,hash,exif,text,password,geometry}/`, `features/privacy/`)

Nine tools, and the module takes **no dependency at all** — WebCrypto, hand-rolled parsers, and arithmetic. The same split as the audio module: pure and unit-tested in `core/`, UI state in the component, one stateless service per tool.

- **`core/crypto/envelope.ts` is the one file in this repo where a regression is irreversible.** A mistake there does not produce a bug report, it produces a user whose file is permanently unreadable. The V2 layout (`"NADASAI_V2"` │ u16**BE** metaLen │ metaJSON │ salt(16) │ iv(12) │ ciphertext), the PBKDF2 parameters and the read order (V2 → V1 `"NADASAI_ENC"`, **eleven** bytes → headerless legacy) are FROZEN. `envelope.spec.ts` pins them with a byte-exact golden vector and three hand-assembled envelopes that must all decrypt; if a change makes those fail, the change is wrong.
- **The iteration count stays at 100 000 even though OWASP now says 600 000.** It is not stored in the envelope, so raising it would silently make every existing `.enc` file undecryptable. Doing it properly needs a V3 header carrying the count, with the V2 reader intact — a deliberate, separate change.
- **Wrong password and corrupt file are cryptographically indistinguishable.** AES-GCM's tag is one bit of information and `SubtleCrypto.decrypt` throws the same bare `OperationError` for both. `crypto_bad_envelope` vs `crypto_decrypt_failed` splits on what happens *before* the decrypt call (does the header parse?), which is the only distinction that actually exists. Do not invent a second one.
- **`core/exif/` is hand-rolled because the STRIPPER is the hard part and no library provides it.** `exifr` reads but does not write; `piexifjs` writes but is JPEG-only. Either way the segment/chunk walker has to be written anyway, so a dependency would add a second parser on top of it and drag CDN-resolved dynamic-import paths into a `require-corp` app. MakerNote is out of scope — proprietary and undocumented — but its presence and size ARE reported, and it is stripped regardless because it lives inside APP1.
- **The strip never decodes the image.** JPEG drops APP1/APP13/APP3-15/COM and copies the entropy-coded scan verbatim; PNG drops the text chunks (its CRC is per chunk, so nothing needs recomputing); WebP drops the RIFF `EXIF`/`XMP ` chunks and must rewrite the size field at offset 4 **and** clear the `VP8X` flag bits. `strip.spec.ts` proves losslessness with TWO assertions — identical decoded pixels *and* an identical post-`SOS` tail — because the first alone would pass for a re-encode at quality 100. What this replaced went through a canvas at quality 0.95, destroyed the ICC profile, turned PNG and WebP into JPEG under their original extensions, and failed silently on the TIFF it advertised.
- **`keepOrientation` writes back a ~32-byte APP1 holding only that tag.** Dropping APP1 takes `Orientation` with it and a portrait phone photo comes back sideways (`exiftool -all=` has the same problem). One integer reveals no camera, place or time, and the scan is still untouched, so the strip stays lossless. TIFF is refused outright rather than half-supported.
- **`redact-pdf` rasterises, and that IS the guarantee.** A black rectangle drawn over a text layer leaves the text in the file — that is how "redacted" documents leak. `drawInvisibleText` from compress-pdf must never be borrowed here; re-adding the text layer is precisely the leak being closed. It needs **no jspdf**: `PdfCompressorService.rasterize` already proved pdf-lib's `embedJpg` does the job, and protect-pdf only reaches for jspdf because pdf-lib cannot *encrypt*. The cost — the whole document loses its text layer, not just the redacted part — is stated in the panel, not just in a comment.
- **`redact-pdf`'s preview separates the two jobs a single scale used to do.** `PREVIEW_SCALE = 1.4` set the on-screen size *and* the raster resolution at once, and there was no zoom at all — so a dense page could not be enlarged to aim a bar at small print, which is the tool's actual work. Now `FIT_SCALE` is display-only (kept at 1.4, so 100% is pixel-for-pixel what it was) and the raster comes from `pageRenderScale()`, the same helper the editor uses, driven by the zoom. Zooming in re-rasterises; zooming out does not, because shrinking a raster that already has resolution to spare is free and refetching would only cost sharpness on the way back. Nothing converts coordinates: `app-region-overlay` emits percentages, so a box drawn at any zoom lands in the same place at every other one — the e2e asserts exactly that, plus the `naturalWidth` growth that separates a re-render from a stretched raster.
- **`clean-pdf-metadata` has two pdf-lib traps, both verified against 1.17.1.** `PDFDocument.load()` defaults to `updateMetadata: true`, which stamps `Producer = "pdf-lib (…)"` and a fresh `ModDate` **on the way in** — a metadata cleaner that fingerprints its own output. And `catalog.delete()` alone leaves the XMP as an orphaned object that the writer still emits, so the author's name stays findable with `strings`; `context.delete(ref)` is required. The spec greps the *decompressed* output bytes for the original author, because object streams would otherwise hide a surviving orphan.
- **Only the black bar is a guarantee; the other mode is a mosaic, not a blur.** Both pixelation and blur have published recovery attacks against low-entropy content — an ID, a card number, a date of birth. Black is the default, the warning is in the panel, and `core/image/redact.ts` says so at the top. In a product called "Nada Sai", shipping a reversible redaction would be the worst possible bug.
- **`core/text/diff.ts` is Myers, unlike its predecessor**, which was labelled Myers, built a full O(m·n) table of boxed numbers inside a `computed()` that re-ran on every keystroke, and assembled the result with `unshift()` in a loop. Prefix/suffix trimming plus line interning is what makes it affordable; the 5000×5000 perf test is the regression guard.
- **All of these tools are on the chain now, and `remove-exif` is the exception that proves why the destinations are filtered.** Its strip is byte-for-byte, so any raster editor downstream decodes it into a canvas and re-encodes — silently undoing the one thing the tool does. `LOSSLESS_SINKS` in `tools.ts` restricts its destinations to encrypt-file and file-hash, the only two that never touch a pixel; the rule lives there, next to the bug it prevents, rather than as a `ToolDef` field the next lossless tool would forget. `encrypt-file` and `file-hash` are the mirror image: `accepts: ['any']` makes them the end of every chain, and the `binary` `FileKind` exists so that a `.enc` — a file with no type anything recognises — can enter the session at all, since reopening one is precisely what encrypt-file is for.

### Background removal (`background-removal.service.ts`)

Unlike the other tools, this doesn't route through `core/image/` — it's a self-contained service, and the file's header comment is the real spec (read it before touching this). Four things carry the design:

- **Two paths, chosen by the input.** `isFlatGraphic()` measures the image; a photo goes to the IS-Net model (`removeWithModel`), a logo/icon/flat graphic goes to a border-sampled chroma key (`removeFlatBackground`). The AI is the *worst* tool for flat art (out-of-distribution → speckle) and the key is the worst tool for hair, so neither is a fallback for the other — the routing thresholds (`FLAT_DOMINANCE`, `FLAT_BORDER_SHARE`) are tuned against real assets.
- **`onnxruntime-web` is imported dynamically and must stay that way** — megabytes of WASM glue that would otherwise land in the initial bundle for someone who only came to crop.
- **The service is stateless (`providedIn: 'root'` but holds no UI signals).** Per-run state lives in the component so Angular destroys it on navigation; it once was a root singleton and that caused stale results and a second concurrent model run fighting the first for the same progress signal. Keep progress/isProcessing in the component.
- **The tool auto-runs, and the chain's history is the guard.** Choosing remove-bg with a file already loaded is as explicit as dropping one, so the component runs on construction — the extra click meant nothing. It runs *unless* `history` already contains `remove-bg`, which is simultaneously the "don't chew on your own transparent output" case and the "don't re-run every time they navigate back" case. That guard is the only thing standing between this and an unconditional auto-run, which is what it was before and why it was turned off.
- **Retouch (`cutout-brush.component.ts`) needs no mask.** The cutout is already a PNG with alpha, so erase is `destination-out` and restore is a stroke whose `strokeStyle` is a `CanvasPattern` of the original — a pattern is anchored at the canvas origin, so it paints back exactly the pixels that were at those coordinates. Strokes are stored as points and undo replays from the pristine cutout: an ImageData snapshot per stroke is ~48 MB on a 12 MP photo. The canvas is always at natural resolution; brush size is in CSS pixels and mapped, so the brush is the size it looks.
- **The engine choice is a licence decision, not just a technical one.** It replaced `@imgly/background-removal` (AGPL-3.0 wrapper — copyleft that reaches a product sold B2B/on-prem, and it fetched weights from a third-party CDN at runtime, defeating the privacy claim). The IS-Net *model* was never the problem (Apache-2.0); only the wrapper was. Don't reintroduce an AGPL or phone-home dependency here.

### SEO (`core/seo/`)

- **`route-map.ts` derives the PT/EN pairs from `TOOLS`**, registering ONE object under both spellings so the halves cannot desync. `alternatesFor()` returns `null` for an unknown path and `SeoService` then **removes** the hreflang tags rather than guessing — the old fallback reused the current path under the other prefix and produced 14 alternates pointing at pages that do not exist. These tags persist across navigations in an SPA, so leaving a stale one makes a page claim to be the previous page's translation.
- **`jsonld.ts` is a pure `buildGraph()`**, so `jsonld.spec.ts` can assert the things that were wrong: no `FAQPage` when nothing is visible, `featureList.length === TOOLS.length` and only on the home page, unique `@id`s, and no `SearchAction`, `aggregateRating` or `review`. The last three are deliberate absences — there is no crawlable `?q=` URL, and fabricated review markup is the most common cause of a structured-data manual action.
- **The FAQ markup cannot drift from the page, because the component that renders REGISTERS.** `FaqComponent` pushes its entries into `SeoService.setVisibleFaq()`; the node is emitted only if that is non-empty *and* its URL matches the current one. The inversion also keeps `tool-content.ts` out of the initial bundle: `SeoService` is root-provided, so importing the copy from there would cost every visitor ~40 KB, whereas the component is only reached from lazy routes. What this replaced injected five hardcoded questions about PDFs onto all 72 URLs, including pages with no FAQ at all.
- **`<app-faq>` renders from `tool-page.component.ts`**, as a SIBLING of the two-shape layout wrapper — inside the loaded grid it would become a third cell, and inside the empty shape it would be squeezed into the 680px dropzone column. One line there gives all 33 tools the section; `[showFaq]="false"` opts a tool out, and parity holds because opting out removes both the markup and the node.
- **`tool-content.ts` covers all 33 tools, and the bar for the 34th is the same.** Four answers *specific* to that tool — its real limits and trade-offs — because four generic privacy answers repeated 34 times is thin duplicate content, which Google treats accordingly. A tool with no entry still falls back to the dictionary's generic set rather than breaking, but `jsonld.spec.ts` now fails on the omission instead of merely reporting it, and enforces a minimum answer length so a padded list cannot pass as coverage.
- **`public/sitemap.xml` is generated** by `scripts/generate-sitemap.mjs` on `prebuild` (also `npm run sitemap`), from the same `TOOLS` array, plus `core/seo/static-pages.ts` for the five non-tool URLs. That file exists separately from `route-map.ts` — which imports it — because the generator loads both TS modules from Node through `transpileModule`, which cannot elide type-only imports, so anything it reads has to be free of runtime dependencies. `sitemap.spec.ts` still fetches the committed file and fails if a tool URL is missing: in a watch loop no build has run, so it catches a stale commit.
- **The 78 URLs are PRERENDERED at build time, and that is what makes the rest of this section reach a crawler at all.** `ng build` runs the app in Node once per route (`prerender: true` + `server: src/main.server.ts`; there is deliberately no `ssr`, no `server.ts` and no express — the output is still only files, which is what keeps "there is no backend" literally true on Cloudflare Pages). Before this, every one of the 72 sitemap URLs served the *same bytes*: one generic `<title>`, no canonical, no hreflang, zero `<h1>` — everything here was written by `SeoService` only after bootstrap, so the measurement was invisible from a browser and obvious to `curl`. Four classes of browser-only code had to yield, and they are the shape of what will break next: a `localStorage` write in a root service's `effect` (`TranslationService`, injected almost everywhere, so it failed *all* 72 routes); `window` keyboard listeners in shell components; a module-scope `const` calling `document.baseURI` (`TESSERACT_PATHS`, which threw in `ModuleJob.run`, before any component existed); and `cancelAnimationFrame` in the audio components' `ngOnDestroy` — the nastiest, because the app is destroyed *after* the HTML is already written, so it killed the prerender worker and took every route still queued on it down in cascade, including `/pt/sobre`. The CLI reports only "error occurred while prerendering route X" and discards the exception, which is why `app.config.server.ts` installs an `ErrorHandler` that prints it. `scripts/spa-fallback.mjs` runs on `postbuild` because Angular renames the shell to `index.csr.html` and writes no root `index.html` (the `''` route is a redirect) — without it `nadasai.com/` is a 404 and the Pages SPA fallback for the legacy URLs disappears. `21-prerender.spec.ts` pins all of it against the real artifact on :4300, fetching bytes with `request` rather than `page` precisely because a browser would hide the bug.
- **The canonical URL form is slash-less and extension-less, and the build is FLATTENED on `postbuild` to make the host agree.** Angular's prerender writes a directory per route (`pt/imagem/cortar/index.html`), which a static host only serves with a trailing slash — so Cloudflare Pages answered **308 on all 72 sitemap URLs**, and the page at the destination then declared `canonical` = the URL that had just redirected. To a crawler that is "page with redirect" plus a canonical pointing back at a redirect, and all 216 hreflang pointed at redirects too, which is precisely the annotation-invalidating shape `route-map.ts` exists to prevent. The fix is not to rewrite the URLs: Pages' own canonical form is already the slash-less one, which is measurable on the live site (`/index.csr` → 200, `/index.csr.html` → 308 → `/index.csr`). So `scripts/flatten-prerender.mjs` renames `rota/index.html` → `rota.html` and the URL every `routerLink`, the sitemap, the canonical and the hreflang *already* emitted starts answering 200. It runs **before** `spa-fallback.mjs` (the root has no `index.html` until that script writes it) and skips the root, which is the SPA fallback and not a route. `public/_redirects` sends the trailing-slash form back to the canonical with a 308 — that form is what Google actually resolved and indexed during the broken period, and after flattening it matches no file, so without those rules it would land on the SPA fallback: 200 serving the empty shell, which is worse than the redirect it replaced. `21-prerender.spec.ts` fetches every `<loc>` in the committed sitemap with `maxRedirects: 0`, because following the redirect is exactly what hid the defect — the content at the end of it was always correct.
- **The sitemap carries `<lastmod>`, derived from git and never from the clock.** It is the only one of the three optional fields Google still reads (`changefreq` and `priority` have been publicly ignored since 2023), and without it the file carried no signal that it had changed: after the privacy module shipped, Search Console kept reporting the **66** URLs of the build before it, and deleting and re-submitting the sitemap only re-showed that same processing. `lastCommitDate()` shells out to `git log -1 --format=%cs -- src public`, so the value moves when the site does and the generator stays deterministic — a wall-clock date would rewrite all 78 entries on every build and claim a change that did not happen, which Google discards anyway. No git, no field: an absent `lastmod` is documented behaviour, an invented one teaches the crawler to distrust the whole file.
- **`src/index.html` carries no canonical and no hreflang.** It is served verbatim for every URL under the SPA fallback, so a canonical hardcoded to `/pt` told every crawler that all 72 tool pages were duplicates of the home page — and Bing and the LLM crawlers never run the JS that would have corrected it.

### Content on a tool page

Toda página de ferramenta fecha com três seções, todas montadas por `tool-page.component.ts` numa linha cada — nenhuma delas existe nos 36 templates:

- **`app-tool-article`** lê `core/seo/tool-article.ts` e renderiza o texto longo (h2 por seção, passo a passo opcional). **Cobre as 36 ferramentas**, PT e EN. O componente ainda não renderiza nada quando falta entrada — é o que permitiu escrever por lotes sem página quebrada —, mas a partir da cobertura completa isso virou teste: `tool-article.spec.ts` exige todas, além de paridade de seções entre PT e EN, piso de 400 palavras por língua e razão mínima entre as duas (o FAQ tinha inglês ~20% mais curto em todas as 36, e é justamente o tipo de decadência que ninguém vê). O arquivo é separado do `tool-content.ts` e ambos só são alcançados por rota lazy, então o texto não custa nada à home.
- **`app-faq`** — as perguntas agora são `h3` (ou `h2` na rota `/faq`, onde o cabeçalho acima é `h1`). Antes eram `<span>` dentro de `<summary>`, e a página inteira tinha um único h2, que era o título do FAQ.
- **`app-related-tools`** lê `relatedTools()` em `tools.ts`, derivado de `accepts`/`produces` como o resto da cadeia. **Duas das quatro vagas são reservadas para outro módulo** e giram com a posição da ferramenta no módulo — sem as duas regras, a seção repetia os links que o rail já dá e as nove páginas de imagem apontavam para os mesmos dois destinos. `remove-exif` continua restrito a `LOSSLESS_SINKS` aqui também: clicar num card navega, navegar commita o arquivo pendente, e recomendar um editor raster desfaria o strip.

Medido no build: `/pt/imagem/cortar` saiu de **223 para 891 palavras visíveis**, de 1 h2 para 6 e de 0 h3 para 3.

### Errors

Every failure path maps through `core/errors.ts` → `toMessageKey(err)` → an `errorKey` signal → `<app-alert>`. A bare `console.error` with no user-visible feedback is a regression — that was the app's single most common defect.

**E agora existe um `ErrorHandler` global no navegador** (`core/errors/global-error-handler.ts`), par do que `app.config.server.ts` já instalava para o prerender: o que escapa de todo `try/catch` de ferramenta — exceção em `effect`, promise rejeitada, callback de biblioteca — vira uma faixa dispensável no topo do `<main>` em vez de uma linha vermelha no console. **Ele resolve `GlobalErrorService` pelo `Injector` dentro do `handleError`, e não como campo:** injetá-lo direto arrasta `TranslationService` → `Router` → `ErrorHandler` e fecha um ciclo de DI (`NG0200`) — cujo modo de falha é o pior possível, porque a partir dali TODA exceção vira NG0200 e a original desaparece. Foi assim que ele escondeu um defeito por um build inteiro, até `36-csp.spec.ts` esbarrar nele.

Dois defeitos silenciosos desta classe foram fechados junto, os dois achados escrevendo e2e: `protect-pdf` tinha `protpdf.error_mismatch` e `error_empty` escritas nos dois dicionários e nunca ditas — com as senhas divergentes o `run()` retornava em silêncio e o botão engolia o clique; e o editor de PDF setava `errorMessage` sem setar `status`, então o banner (`status() === 'error' && errorMessage()`) nunca renderizava e soltar um `.txt` ali não produzia reação nenhuma.

**The rejection at the door speaks for the module that rejected**, which is `rejectionFor(accepts)` in `workspace.service.ts` and not a single code. `unsupported_file` reads "não é uma imagem suportada. Use PNG, JPEG, WebP…" — it was written when the image module was the only one with a session and the type guard still lived in its `apply()`. Moving the guard up to the pick-up made that one sentence answer all five modules, so dropping a `.txt` on "Comprimir PDF" replied by recommending PNG. Every tool's `accepts` holds exactly one kind, so the map is direct; a new kind that reaches the default gets the image copy and needs its own code.

### i18n

Hand-rolled, not `@angular/localize`. `TranslationService` derives `TranslationKey` from the EN dictionary and types PT as a total `Record` over it, so **a missing key is a compile error**. **O que a tipagem NÃO pega é texto que nunca virou chave**, e havia 25 dessas cravadas no HTML de sete ferramentas — "Texto Extraído", "Cor da Caneta", "Gerando miniaturas das páginas…", os rótulos de taxa de amostragem, e as abas do assinar, cujas chaves EXISTIAM nos dois dicionários e eram simplesmente ignoradas. Todas apareciam em português no meio da interface em inglês; todas foram para o dicionário. É a mesma classe do `alt` em português que a auditoria achou, um nível mais fundo — e a única defesa contra ela é olhar o template, porque o compilador não tem do que reclamar.
 (The compress button once rendered with no label at all because its key simply didn't exist.) Templates read `i18n.t()['some.key']` — bracket access is mandatory under `noPropertyAccessFromIndexSignature`. A spec asserts key parity between languages.

### Offline, PWA and the proof

The app is a service-worker PWA, and that is downstream of the privacy claim: a tool that never uploads has no reason to need the network twice. Four services carry it, each with its own header comment worth reading before you touch it.

- **`ngsw-config.json` splits assets by cost.** `app` and `assets` prefetch; `ai` (`model/`, `ort/`) and `pdf` (`pdfjs/`, `tesseract/`, `tessdata/`) are **lazy** — prefetching 42 MB of weights on first paint would make the home page feel broken. A new runtime asset directory that isn't listed here works online and disappears offline.
- **`AppUpdateService` blocks the screen between `VERSION_DETECTED` and the reload**, on purpose: once ngsw swaps the manifest, the lazy chunk the old page asks for on the next click may not exist, and the user gets a chunk-load error instead of a tool. It stays invisible when nothing needed downloading.
- **`ModelPrefetchService` exists so the rule in `BackgroundRemovalService` can stay intact.** Per-run state belongs to the component; a 42 MB download is global, idempotent and outlives navigation, so it lives here — and it awaits the *same* memoised promise the real run uses, so a prefetch in flight *is* the first run's download.
- **`NetworkProbeService` is an instrument, not a claim.** It wraps fetch / XHR / sendBeacon / WebSocket and counts **file egress only** — a body carrying a File, Blob, ArrayBuffer, typed array, or FormData containing a File. Counting all outbound bytes was tried and is wrong in both directions: a login or a checkout would light it up the day billing ships, and a corporate antivirus doing TLS interception (Kaspersky, on the machine this was built) injects a script that POSTs its own telemetry — which had the product accusing itself, on its own home page, of the one thing it exists to prevent. `09-offline` and `08-proof` in the e2e suite guard this behaviour, and `09-offline` is the reason Playwright boots a real production build on 4300.
- **The meter is shown on every route, and that placement is the point.** It used to be a 380px card on the home page only — which put it on the one screen where no file is in play, and removed it the moment someone opened a real document. `app-network-badge` is the reading at the size of a button (top bar, `sm`; home hero, `md`), and `app-network-proof` is now its popover contents rather than a card: the disclosure of what the page *does* fetch stayed, it just stopped costing a column. Going offline shows on the pill itself instead of waiting behind a click, because that is the moment the claim is easiest to believe. The cost is that the meter joined the initial bundle (537 → 546 kB), which is exactly what being on every screen buys. The numbers are live readings and never copy — hardcode a zero and this is just another privacy promise with nicer typography.

**A CSP é a tese do produto escrita de um jeito que o navegador obriga**, e mora em `public/_headers` junto com COOP/COEP. `NetworkProbeService` MEDE a saída de arquivo; `connect-src 'self' data: blob:` IMPEDE — uma dependência com telemetria, uma linha nova ou um script injetado por antivírus corporativo deixam de conseguir mandar o arquivo embora, em vez de serem contados depois. As diretivas que não são óbvias estão comentadas no próprio arquivo; a que mais dói é `script-src-attr 'unsafe-hashes' 'sha256-Mht…'`, que libera EXATAMENTE o `onload="this.media='all'"` que o Angular embute ao inlinear o CSS crítico — sem ela a folha de estilo fica em `media="print"` para sempre e **o site aparece sem CSS nenhum**, sem erro. `e2e/preview-server.mjs` agora LÊ o `_headers` de verdade em vez de repetir uma cópia, e `36-csp.spec.ts` roda PDF e OCR com a política aplicada e falha se qualquer violação disparar — uma diretiva apertada demais quebra a ferramenta em silêncio.

**O service worker registrado é `nadasai-sw.js`, não o `ngsw-worker.js` direto.** Ele é três linhas em volta do worker do Angular: um listener de `fetch` registrado ANTES do `importScripts` (quem chama `respondWith` primeiro vence) que atende o POST do Web Share Target, guarda o arquivo no Cache Storage e redireciona com 303. `core/services/share-target.ts` é a metade cliente, e a leitura APAGA a entrada — num produto cujo argumento é que nada fica guardado, ressuscitar o último arquivo compartilhado semanas depois seria a pior forma de vazamento possível. Todo o resto (precache, atualização, offline) continua sendo o ngsw.

**`/pt/abrir` e `/en/open` são onde o sistema operacional entrega arquivo** — `file_handlers` ("Abrir com") e `share_target` (folha de compartilhamento do Android), os dois declarados no `manifest.webmanifest`. A página não transforma nada: detecta o tipo e oferece o que o produto faz com aquele tipo, pela mesma `nextToolsFor` da cadeia. Fica fora do sitemap e do `static-pages.ts` de propósito. O manifesto também ganhou `id`, `shortcuts`, `launch_handler` e — o que faltava para o Chrome no Android sequer OFERECER a instalação — ícones PNG de 192 e 512, mais um `maskable` separado (declarar o normal como maskable é o erro que corta as bordas do logo). Os três saem do `npm run og`, junto com os cards sociais, e `og-cards.spec.ts` falha quando algum deles não existe.

## Design system

`src/styles.css` is the whole thing — there is no `tailwind.config.js`. It resets Tailwind's stock scales (`--color-*: initial`, `--radius-*`, `--text-*`, `--font-weight-*`, `--shadow-*`) and redefines only what the product uses. **`bg-teal-600`, `font-black`, `rounded-3xl`, `text-6xl` and `shadow-xl` therefore generate no CSS at all.** That is deliberate: the previous design read as machine-generated, and this makes the old look unreachable rather than merely discouraged.

The palette is Tailwind's **slate** ramp with a **blue** accent, on **Nunito** (self-hosted via `@fontsource/nunito`, weights 400–700 only — a webfont CDN would be a network request on every load, which contradicts the privacy claim and breaks the app offline). `@fontsource/inter` is still in `package.json` but nothing imports it; the typeface is Nunito.

**There is one theme and it is light.** The app used to ship a dark default plus a sun/moon toggle; both are gone, there is no `ThemeService`, and `:root` declares `color-scheme: light` with a single set of values. Two consequences: a `dark:` variant or a `prefers-color-scheme` block in a component is dead code, and every foreground token is tuned for **WCAG AAA against white** (`--muted` at 9.5:1, `--accent` at 7.5:1) — pick an existing token rather than a lighter shade of one. The header comment in `styles.css` and the `colorScheme: 'dark'` line in `playwright.config.ts` still describe the two-theme era; the tokens below them are the truth.

Rules the tokens enforce:

- Headings cap at 28px; font weights cap at 600.
- Containers are separated by `border border-line` (1px), not shadows.
- Numbers (sizes, dimensions, percentages) use `font-mono tabular`.
- Radii: 6px controls, 8px panels, 10px the preview stage.

Five things about the colour tokens are load-bearing:

- **Never hardcode a hex in a component** — add a semantic token in `styles.css`. Every colour resolves through a variable, which is what made deleting a whole theme a token edit rather than a sweep through templates.
- **Depth is page-vs-card plus a 1px line**, never a heavy shadow: `--base` sits a shade below pure white (`#e9edf3`) so the white surfaces lift on their own.
- **`accent` and `accent-fill` are different jobs** even though they currently hold the same blue. `accent` is the foreground (links, active tool, focus rings); `accent-fill` is the solid behind white text (primary button, with `--on-accent` as its text). They are separate tokens so a future accent that must lighten for legibility can move without turning every primary button pastel.
- **The rail has its own foreground tokens** (`text-rail-muted`, `bg-rail-hover`, `bg-rail-active`, …) and anything rendered on it must use them, never `text-white/50` — literal white on the light rail is invisible, and that is exactly how light mode read as broken back when the rail was dark. `<app-segmented onRail>` exists for this.
- **Each tool's `tone` needs a `--tone-<name>-fg` / `--tone-<name>-bg` pair**, and the foregrounds are deliberately dark (`amber` is `#92400e`, not amber-500) because they carry text on a tinted badge at AAA.
- **The image stage (`bg-stage`) is the one dark surface left, and it survived the theme deletion for a reason** — a light surround visibly skews how you judge an image's brightness. But it is only for surfaces that actually *contain the image*: the empty dropzone is themed, because a black slab on a light page is just a black slab.
- **A document you read is not an image you judge, so it gets `bg-doc-stage` instead.** The PDF editor's scrolling page surface is the one place that reads a whole document rather than inspecting a picture, and the reason `bg-stage` is dark does not reach it — nobody colour-grades a transcript. Near-black there fights the white page for attention and glares over a long read, which is why Acrobat, Preview and Chrome's own viewer all use a neutral mid grey. The page itself is a sheet: 6px radius, and `shadow-page` — a 1px ring so white does not bleed into the grey, a short shadow to seat it, a long one for height. The page wrapper deliberately has no `overflow-hidden` (a selected block's resize handles sit at -4px and its move handle at -14px, and would be clipped); the canvas carries the radius, since canvases honour `border-radius` when painting.

  **Every tool that shows PDF pages uses this surface, not just the editor** — merge, organize, split, pdf-to-img, compress, protect, sign, watermark, img-to-pdf and the audio cutter. It used to be only the editor, and the rest were left on `bg-stage` with the argument that small previews on a dark backdrop read as a lightbox. That argument was wrong twice over: it made the module look like two products (the editor bright and framed, everything beside it a black slab), and a lightbox is for *looking* at something, whereas nobody reordering page four is judging its exposure. The rule that survives is the one about what the surface is FOR: dark for an image whose brightness you are judging, grey-plus-sheet for a document you read, scrub or rearrange. `app-page-grid` follows it, so its tiles are sheets — white, 6px, `shadow-page` — and its drag-over state is an `outline` rather than a border, because `shadow-page` already carries a 1px ring and a second border would double it. The image tools (crop, remove-bg, and `app-preview-surface` / `app-compare-slider` under them) keep `bg-stage`, which is exactly the case the token was written for.

Icons go in `shared/ui/icon/icons.ts` and render via `<app-icon>`; inline `<svg>` in a template is not the pattern.

## Conventions

- Angular 19 control flow (`@if` / `@for`) — `*ngIf`/`*ngFor`/`ngClass` are gone and should stay gone.
- Signal-based inputs (`input()`, `output()`, `model()`), `ChangeDetectionStrategy.OnPush`, `inject()`. Standalone components only; there is no NgModule.
- Every route is `loadComponent`, so a heavy dependency reached by exactly one tool costs only that tool — which is the whole reason the dynamic `import()`s above are worth defending.
- TypeScript `strict` with `strictTemplates` and `noPropertyAccessFromIndexSignature`. No linter (see Commands).
- Production budget errors at 1 MB initial. Heavy deps must stay in lazy chunks — re-measure with `npm run build` rather than trusting a number written here.
- UI copy is in the dictionary in both PT and EN; comments and commit messages are mixed PT/EN, and both are written to explain *why*, often naming the bug the code exists to prevent. Match that when you touch a commented block: a comment that only restates the line is worse than none.
